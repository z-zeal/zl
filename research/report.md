# MIR Architecture — Experimental Evaluation

*An experimentally measured evaluation of ZL's mid-level IR (MIR) as the
compiler boundary: the existing AST→bytecode compiler against the MIR-based
pipeline, and unoptimised MIR against optimised MIR.*

All numbers in this document are **measured**. They come from the compiler's
own `--artifact-stats` stage ledger (per-stage millisecond timings and artifact
sizes) and from wall-clock / `wait4` rusage of real process runs, collected by
`research/harness.py` over the corpus in `research/corpus/`. Nothing is
estimated beyond what the measurements support, and where an interpretation is
uncertain that is said explicitly. Raw data: `research/results/results.json`
(regenerated by the harness; kept out of Git as a large, ephemeral artifact).

## 1. Method

### 1.1 Environment

| Item | Value |
| --- | --- |
| Revision | `464efb99de34266682881caa225799ad3a5d4bd1` (branch `arena/01a09514-zl`) |
| Compiler | GCC 12.2.0 (Debian 12.2.0-14+deb12u1), C++17 |
| Build | `cmake -S . -B build -DCMAKE_BUILD_TYPE=Release` |
| Host | Linux x86-64, 2-core virtualised sandbox |

Absolute timings are host-specific; the *relative* comparisons (reference vs
MIR, unoptimised vs optimised) are the signal and are what this report reasons
about.

### 1.2 Measurement configurations

Four compile configurations and three run configurations per program:

| Label | Command | Meaning |
| --- | --- | --- |
| `ref` | `zl --reference-compiler` / `--artifact-stats --reference-compiler` | the existing AST→bytecode compiler, kept unchanged |
| `mir-unopt` | `ZL_MIR_OPT=0 zl --mir-vm` | MIR pipeline, optimisation stage off |
| `mir-opt` | `zl --mir-vm` | MIR pipeline, default (run-path) optimisation |
| `native` | `--artifact-stats --backend=native` | MIR pipeline with the native backend |

Timings are per-stage minimums over 3 compiler invocations; runtime is the
median (and minimum) over 5–12 executions. Peak memory is `ru_maxrss` of the
single measured child process (fork/exec/wait4), so it is per-run, not
cumulative.

### 1.3 Corpus

`research/corpus/` contains 16 positive programs, one per language feature area
requested, each a single file whose stem matches its class and whose `main`
produces deterministic output (so output equivalence is a machine-checkable
correctness oracle):

| # | Category | Program | What it exercises |
| --- | --- | --- | --- |
| 1 | primitive computations | `Prims.zl` | int/double/bool/string arithmetic, bitwise, comparisons |
| 2 | control flow | `ControlFlow.zl` | if/elif/else, for/while/repeat, break/continue, match |
| 3 | recursion | `Recursion.zl` | fib(26), factorial, mutual recursion, structural recursion |
| 4 | generics | `Generics.zl` | user generic class + `List`/`Map`/`Set` incl. nested `Map<string,List<int>>` |
| 5 | unions | `Unions.zl` | `int\|string`, match narrowing, `Option`, `Result` |
| 6 | collections | `Collections.zl` | List/Map/Set/array literal/Queue/Stack |
| 7 | objects | `Objects.zl` | fields, constructor, encapsulation, independence of instances |
| 8 | inheritance | `Inheritance.zl` | extends, `super()`, `@Override`, virtual dispatch |
| 9 | interfaces | `Interfaces.zl` | interface, `implements`, interface-extends-interface, dispatch |
| 10 | closures | `Closures.zl` | lambdas, by-value capture, closure state, higher-order `func` |
| 11 | ownership | `Ownership.zl` | `owned`/`move`/`borrow` |
| 12 | exceptions | `Exceptions.zl` | throw, try/catch, finally, custom exception types |
| 13 | tasks | `Tasks.zl` | `async func`, `await`, `Task<T>`, `block()` |
| 14 | concurrency | `Concurrency.zl` | Thread/Shared/Atomic/Mutex/Channel |
| 15 | native resources | `NativeResources.zl` | OS file create/read/append/delete |
| 16 | FFI | `Ffi.zl` | `@ffi(library, symbol)` / `@ffi(symbol)` declarations |

`research/corpus/safety/` adds 10 adversarial programs: 6 expected to be
rejected **statically** (type mismatch, union mismatch, return mismatch,
use-after-move, move-while-borrowed, thread-boundary capture) and 4 that are
statically accepted but whose violation is a **runtime** obligation
(out-of-bounds, division by zero, `Option.unwrap()` on `None`, a dynamic→static
type boundary).

`research/corpus/limitations/` holds 3 programs that expose known lowering or
verification gaps (see §3.7).

## 2. Results

### 2.1 Successful lowering and MIR verification

| Metric | Result |
| --- | --- |
| Positive corpus programs | 16 |
| Fully lowered (`--artifact-stats` ok) | **16 / 16** |
| Verified clean (0 verifier errors, 0 incomplete functions) | **16 / 16** |
| MIR verification failures in the positive corpus | **0** |
| MIR verification failures in the limitations corpus | **1** (`InterfaceStaticParam.zl`, see §3.7 — `FixedArrayNative.zl` now verifies after `isCollectionType` fix) |
| Output equivalence ref vs MIR (optimised and unoptimised) | **16 / 16 identical** |

Every positive program lowered, verified, ran, and produced byte-identical
output under the reference compiler, the MIR pipeline optimised, and the MIR
pipeline unoptimised. The optimiser's differential guarantee (a pass that
breaks equivalence is rolled back) holds on this corpus. `FixedArrayNative.zl`
previously failed verification and now passes (fixed; see
docs/changelog.md, 2026-09-17).

### 2.2 Compile time

Median per-stage time across the 16 positive programs (ms; lower is better):

| Stage | reference | MIR unopt | MIR opt | MIR native (opt) |
| --- | ---: | ---: | ---: | ---: |
| load | 1.66 | 1.65 | 1.62 | 1.64 |
| semantic analysis | 3.86 | 3.77 | 3.84 | 3.70 |
| typed lowering → MIR construction | — | 4.19 | 4.19 | 4.14 |
| MIR verification | — | 6.31 | 6.35 | 6.24 |
| MIR optimisation | — | 0.00 | **43.90** | 43.66 |
| code generation | 2.49 (AST→bytecode) | 9.60 | 9.53 | 13.50 (native) |
| **total** | **8.46** | **26.30** | **69.56** | **73.53** |

Key measured facts:

* **MIR construction costs ~10.5 ms** (4.19 ms lowering + 6.31 ms verification)
  above the shared front end. That is the price of the typed, verified boundary.
* **The optimiser is the dominant cost of the shipped path**: +43.9 ms, which is
  **63% of the optimised total**. Unoptimised MIR compiles in 26.3 ms; turning
  the optimiser on more than doubles it to 69.6 ms.
* **The MIR bytecode backend is ~3.8× slower to run than the reference code
  generator** (9.53–9.60 ms vs 2.49 ms) for the same module.
* The reference compiler ends-to-ends in **8.46 ms**; MIR-unopt is **3.1×**
  that and MIR-opt is **8.2×** that.
* Native code generation (13.50 ms) is ~1.4× the bytecode backend's.

### 2.3 Generated code size

Median artifact sizes across the 16 positive programs:

| Artifact | reference | MIR unopt | MIR opt |
| --- | ---: | ---: | ---: |
| Bytecode (bytes) | 218,720 | 325,880 | 309,720 |
| Bytecode (instructions, 40 B each) | ≈5,468 | ≈8,147 | ≈7,743 |
| MIR instructions (lowered module) | — | 2,233 | 2,052 |
| Native machine code (compiled subset) | — | — | 1,185 bytes / 5 functions |

* **MIR-derived bytecode is ~49% larger than the reference compiler's output
  (unoptimised) and ~42% larger after optimisation.** The reference chunk's name
  pool is larger, but the MIR backend emits substantially more instructions.
* **The optimiser removes a median ~181 MIR instructions (≈8%) and ~400 bytecode
  instructions (≈5%).** It is real, just small on this corpus.
* **The native backend compiles 5 of ~292 module functions** (the deliberately
  small primitive subset); the other ~287–288 are left to the VM, which is the
  dominant structural limitation of the native tier today (§3.7).

### 2.4 Runtime performance

Median end-to-end wall time (compile + execute) and the execution-only estimate
(wall − measured compile time), milliseconds:

| Program | ref wall | mir-opt wall | mir-unopt wall | ref exec | mir-opt exec | mir-unopt exec |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Prims | 527 | 639 | 642 | 519 | 568 | 617 |
| Recursion | 558 | 813 | 775 | 549 | 745 | 750 |
| ControlFlow | 51 | 151 | 111 | 43 | 83 | 86 |
| Collections | 72 | 151 | 103 | 63 | 48 | 73 |
| Concurrency | 233 | 315 | 299 | 225 | 246 | 272 |

Two distinct effects are visible and are separated here deliberately:

1. **End-to-end, optimised MIR is the slowest configuration** — but this is
   almost entirely the optimiser's fixed ~44 ms compile cost, not execution.
   Subtracting compile time, optimised and unoptimised MIR execute essentially
   identically (Recursion 745 vs 750 ms; ControlFlow 83 vs 86 ms).
2. **MIR-derived bytecode executes slower than the reference compiler's
   bytecode** for compute-heavy programs (Prims +9%, Recursion +36%,
   Concurrency +9%), consistent with the ~40% larger instruction stream running
   on the same interpreted VM. On the small method-call-heavy program
   (Collections) the difference is not consistent and is within noise.

Correctness across all three configurations is byte-identical for all 16
programs, so the slowdown is not a semantic change.

### 2.5 Memory behaviour

Peak process RSS (KB) during a run:

| Configuration | typical peak RSS |
| --- | ---: |
| reference | ~11.2–11.6 MB |
| MIR unoptimised | ~11.8–12.9 MB |
| MIR optimised | ~14.6–15.3 MB |
| Concurrency (any) | ~142–160 MB (threads + GC) |

The MIR path costs roughly **+3.4 MB peak RSS** (the MIR module, verification
and optimisation working set, and the larger chunk) over the reference path.
Optimisation adds a further ~2–3 MB over unoptimised MIR.

### 2.6 Safety: static vs runtime

Measured with `--safety-check` over the 10-program safety corpus:

| Layer | Result |
| --- | --- |
| Static-reject programs (6) | **6 / 6 rejected at the semantic (type-checker) layer** — type, union, return, move, borrow and thread-capture violations are all caught before MIR |
| Runtime-check programs (4) | **4 / 4 statically verified**, and **4 / 4 demonstrated a caught runtime check** (bounds, division-by-zero, `unwrap()` on `None`, dynamic→static `refine`) |

`--safety-check` on a representative verified program reports **318
diagnostics, all warnings, 0 errors**: 196 `dynamic-boundary` and 122
`native-call`. These are the machine-visible form of "runtime checks remain an
obligation": dynamic values crossing into typed slots (`refine`) and calls into
native code are checked at runtime, not proven statically.

Historical note: §3.7 previously recorded `FixedArrayNative.zl` as a verifier
rejection (silent type-erasure turned into loud refusal). That gap is now fixed
by `src/mir/type.cpp` `isCollectionType` including `Array`; the fixture now
verifies clean.

### 2.7 Failures and limitations (measured, not inferred)

1. **`FixedArrayNative.zl` — previously MIR verification failure, now fixed.** Passing
   `array[5]<int>` through `Collection.length`/`Collection.get` previously lowered
   the element type to `list<unknown>` and verifier rejected it. Fixed by
   `src/mir/type.cpp` `isCollectionType` including `Array`. Fixture now
   verifies clean and runs; kept as regression.
2. **`InterfaceStaticParam.zl` — unsupported lowering.** Passing an
   interface-typed value as an argument to a *static* function is not lowered
   ("unsupported call … not lowered"); the function is marked incomplete and
   its call site is stubbed (fail-closed). Direct virtual dispatch through an
   interface-typed variable works; only the static-parameter spelling is
   unlowered.
3. **`BareFuncParam.zl` — honest `unknown`, not an erasure.** A bare `func`
   parameter carries no signature, so MIR records the parameter type as
   `unknown` rather than inventing a type. The module still verifies, and the
   higher-order call happens through the runtime boundary. This is the
   documented "8 lowering notes" root cause from `docs/mir.md`, reproduced
   here.
4. **Native coverage.** Across the corpus the native backend compiles ~5 of
   ~292 functions (1.7%) and 1,185 bytes of machine code; everything else —
   including all collection, closure, task, thread and FFI-body code — is left
   to the VM. The native tier is a code generator for a primitive subset, not
   yet a competing backend.
5. **Parser-level findings surfaced while building the corpus** (not MIR
   defects, recorded for completeness): previously a block-bodied lambda could
   not declare typed parameters, but `func(int x) { return x*2 }` now compiles;
   the untyped block-body form `func(x) { return x*2 }` was the last such
   gap and is fixed too (docs/changelog.md, 2026-09-17). `list`/`map`/`set` are reserved words usable as type names but
   not variable names (P1-4).

### 2.8 Allocation baseline (memory-domains Phase 0, measured 2026-09-19)

The memory-domains plan requires each phase's §10 numbers to land here. The
[Phase 0 gate](../docs/memory-domains.md#101-phase-0-baseline-measured-2026-09-19)
asks: `new` throughput, GC pressure, and per-object memory cost, before and
after making the existing collector pay — no language surface, implementation
only. Workload: `benchmarks/AllocationBenchmark.zl`, one process per
configuration (`benchmarks/run_allocation_benchmark.sh`, per-child peak RSS via
`wait4`, two runs averaged). Machine: 2-core x86-64, 3.9 GB RAM, Linux, g++ 12,
`-O2`, single-threaded VM. "Before" is `3f1a737` + measurement counters only;
"after" adds (a) flat `ObjectBox::fields` + per-class `name → index`, (b)
recycled-box free lists, (c) the growth policy (already in the baseline).

| workload | alloc/s before → after | Δ | collect share before → after | peak RSS before → after | Δ |
| --- | --- | --- | --- | --- | --- |
| one-field, keep 1e5 | 133.4k → 135.4k | +2% | 1.1% → 1.1% | 80.9 MB → 66.5 MB | −16% |
| one-field, keep 1e6 | 129.5k → 120.8k | −7% | 4.3% → 4.2% | 682.3 MB → 559.3 MB | −18% |
| one-field, churn 1e6 | 146.8k → 141.5k | −4% | 1.4% → 1.8% | 18.4 MB → 18.3 MB | −3% |
| eight-field, keep 1e5 | 53.6k → 55.3k | +3% | 1.1% → 0.7% | 153.8 MB → 98.0 MB | −36% |
| eight-field, keep 1e6 | 53.8k → 55.2k | +2% | 4.2% → 2.8% | 1410.5 MB → 874.4 MB | −38% |

Reading: **the memory win is the flat fields** — peak RSS per kept object
(Δ keep 1e5 → keep 1e6) drops **703 B → 574 B (−18%)** one-field and
**1464 B → 905 B (−38%)** eight-field, and the eight-field collect share drops
4.2% → 2.8% because tracing walks a vector, not a hash table. **Throughput is
neutral** (every Δ inside two-run variance); recycling's free list hits ~100%
in churn yet buys no speed — the per-allocation cost is the registry
`push_back` and the refcount, not the box allocation. Gate verdict (§10.1):
what (a)+(b)+(c) cannot buy is eager release at scope exit, which is exactly
what the domain phases exist to measure against this table. Raw rows:
`benchmarks/results/allocation_{before,after}{,2}.json`.

## 3. Trade-off analysis

**What MIR costs (measured).** The boundary is not free. MIR construction and
verification add ~10.5 ms over the shared front end; the shipped optimiser adds
a further ~43.9 ms; the MIR bytecode backend is ~3.8× slower than the reference
code generator; MIR-derived bytecode is ~42–49% larger and ~9–36% slower to
execute on compute-heavy programs; peak memory is ~3.4 MB higher. Net: a
default compile is ~8.2× the reference's 8.5 ms, and an optimised run's
end-to-end latency is *higher* than an unoptimised one because the optimiser's
fixed cost is not recouped at runtime on these workloads.

**What MIR buys (measured).** A single verified boundary that both backends
consume byte-identically (`--pipeline-report` reports the same MIR digest for
bytecode and native on every program); 16/16 differential output equivalence
between reference, optimised MIR and unoptimised MIR; a differential-checked
optimiser whose every pass is rolled back on divergence; and a static safety
layer that caught 6/6 source-level violations at the type checker and 1/1
type-erasure bug at the verifier that the reference compiler silently accepts.

**The optimiser specifically.** On this corpus the optimiser reliably shrinks
the module (~8% of MIR instructions, ~5% of bytecode) but produces **no
measurable speedup** — because it is deliberately conservative: it never
reorders, sinks, hoists, inlines or transforms loops, and the hot-loop MIR
(`Recursion.fib`, `ControlFlow.main`'s loop, `Collections.main`'s loops) is
byte-identical before and after optimisation (verified by diffing `--emit-mir`
vs `--emit-mir-opt`). Its value today is size reduction and the proof
infrastructure that makes the boundary trustworthy, not execution speed; for
short-running programs it is a net compile-time cost. The measured execution
difference between optimised and unoptimised MIR is within run-to-run variance
once compile time is subtracted.

**The native tier.** Real machine code is produced (x86-64, relocation-resolved,
~1,185 bytes for the 5-function subset), but at ~1.4× the bytecode backend's
code-generation time and for ~1.7% of the functions in a realistic module. It
is a correctness artifact and a boundary demonstration rather than a
performance path today.

## 4. Threats to validity

* **Single host.** All timings are from one 2-core virtualised sandbox; absolute
  values will not reproduce elsewhere. Relative rankings were stable across
  re-measurements, but cross-host confirmation is outstanding.
* **Corpus size.** 16 positive + 10 safety + 3 limitation programs exercise each
  requested feature but are not a broad workload corpus; the shipped
  `examples/` (59 files) and `stdlib/` (26 modules) remain the wider
  differential set (50/50 and 76/76 identical per the project's own harnesses).
* **Runtime noise.** GC pauses and thread scheduling (Concurrency) are
  nondeterministic; medians/minima over 5–12 runs reduce but do not eliminate
  noise. The "execution-only" column is a subtraction of a separately measured
  compile time and is an estimate, not a direct measurement.
* **Optimiser runtime comparison.** Because hot code is byte-identical after
  optimisation, the optimised-vs-unoptimised runtime difference is dominated by
  compile time; statements about execution speed are therefore weak and are
  flagged as such.

## 5. Conclusion and recommendations

MIR is functioning as an evaluated research artifact: 100% lowering and
verification success on the positive corpus, backend independence proven by
digest parity, differential-equivalent optimisation, and a static safety layer
that catches a class of error the reference compiler lets through. The measured
cost is concentrated and actionable:

1. **Bytecode quality parity.** The MIR bytecode backend emits ~42–49% more
   instructions than the reference compiler, which shows up directly as ~9–36%
   slower execution. This is the highest-value gap to close.
2. **An optimiser time budget.** The fixed ~44 ms optimiser cost dominates small
   programs; a size- or time-bounded default (or early exit when a pass set is
   exhausted) would recover most of the 8.2× compile-time multiplier without
   touching the passes' guarantees.
3. **Close the remaining lowering gap** pinned in §3.7 (interface-typed static
   parameters — fixed-array element types through native collection primitives
   is now fixed) — the remaining one is a standalone corpus reproduction.
4. **Grow the native subset** beyond ~1.7% of functions if native compilation is
   to become a measured performance contribution rather than a demonstration.

The corpus, harness, and this report live under `research/` so the evaluation
is re-runnable (`python3 research/harness.py`) and auditable rather than a
one-off claim.
